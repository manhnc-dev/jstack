# Exercise: stack-level verification on acme-pass

Date: 2026-11-11, 15:37Z to 17:51Z. Repo: acme-pass at `c2b2d58b` (Spring Boot, Gradle, JUnit 5, JDK 21). Feature: the session-scoped preferences API, the same requirement as the first acme-pass run. Tool: jstack at `0647428`, the first commit with `/jstack:verify-stack`.

## Question

Earlier runs produced one verification report per PR and nothing that said the feature works end to end. This run asks whether the new stack step gives that answer, and what it costs.

## Method

One coordinating agent, unattended, in a fresh worktree on `compare/jstack-e2e/base`: init, plan, pr-plan, `build --no-gate`, verify-stack. Slug `preferences-api-e2e`. Operator rulings: no push, no `gh`, no app boot, no downloads, one Gradle run at a time, component tests through `MockMvcBuilders.standaloneSetup`, blackbox boot recorded as unavailable. 33 subagents, all native `jstack:` types, none lost.

After the run I re-ran every checker myself from the plugin checkout: `check-stack.mjs`, `check-verification.mjs` on PR-1 to PR-5, and `check-findings.mjs` for both stages all exit 0, and no `*.log` or `rerun-*` file is tracked.

## What the stack step showed

- It answers the question. One table says which scenarios are proven and at which tier, and the verdict word carries the gap instead of a footnote.
- PARTIAL was the honest verdict. Every per-PR report said PASS; only the stack report says the feature has never answered a request as a deployed process.
- S-22 (storage failure becomes 500) is `@Disabled` in the blackbox suite, because a test cannot make the real MongoDB fail on demand. It would stay `not run` on a fully equipped machine, so this plan cannot reach PASS as written. The stack table made that visible; nothing per PR did.
- The disposition rule worked as designed. Both audit lanes on PR-5 found that the `blackboxTest` Gradle task could be reported UP-TO-DATE and send no request. Three findings were disposed `fix`, the checker forced FAIL, a fix round ran, and three fresh workers re-verified to PASS.
- The scenario-id title rule made the mapping mechanical: `scenarios.txt` was generated by a script from the JUnit XML and the plan tables.

## What it did not show

No blackbox test ran. A spike before the run booted the jar past the datasource against an H2 server in MySQL mode and an in-memory Mongo stub, then stopped at Redis: the app builds its own Lettuce connection factory, and Lettuce's handshake needs a real redis-server. Running one from a downloaded jar was refused by the sandbox. Until a redis-server is on the machine, PASS is out of reach here.

Two audits (A1 on PR-3 and PR-4) returned zero findings in under a minute. The coordinator re-read the PR-4 component cases by hand and found nothing; a fast empty audit is still a weak signal.

Fixed in the commit that carries this log:
