## Stage 1. Grounding

One explorer, 2 minutes, 14 tool calls. It returned every handler signature with line numbers, the service interface, the session and exception types, the interceptor path patterns, and the test support helpers. Three findings changed the requirement before any plan was written:

- Seven preference handlers exist, not six. `GET /{id}/preferences/{name}` was missing from the requirement table.
- The requirement said "401". The handlers turn `UnauthorizedException` into HTTP 400 with `AUTHORIZATION_ERROR`, and the tests pin that. The requirement now says 400.
- `/api/v1/preferences` is not in `RequestHeaderInterceptor`'s path patterns, so a new controller would never see a session. The plan must touch `WebMvcConfig`.

The requirement was amended and the plan-branch commit re-made as `f99ccbe8`. This is the "never block on the human for an observable fact" principle doing its job. The grounding report was saved for the planner so it reads one file instead of the repo.

## Stage 2. Implementation plan

Planner (opus): 4 minutes, 12 tool calls, checker clean on the first run I made. Output `docs/jstack/preferences-api/implementation-plan.md`, 350 lines: 10-line summary, 6 sequence diagrams, 26 change rows across 4 product files, 26 test rows across 5 test files, risks naming the coverage floor and the size of the new controller.

The planner made one design call I had not given it and it was right. The operator guidance said the shared service should keep "the same catch blocks". The planner found that `AppException extends AcmePassException`, so a catch in the shared method would turn a 500 into a 400 on the old endpoints. It left the catches in the controllers and flagged the deviation. That is the "diagrams carry the detail" principle paying off: the flaw was visible in SD-2 before any code existed.

Reviewer (opus, read-only): 90 seconds, 4 findings, none blocking. Two were real test gaps: no old-endpoint test pins admin access on six of the seven handlers, and none pins a service-thrown 400 surviving delegation. Both are cheap new cases and I added them to the test rows. The other two were a logging note for the new catch blocks and a type name in the summary. The reviewer also confirmed every signature in all six diagrams against the code and that no reflection-based test enumerates the preference handlers.

Human gate: I read the summary and SD-1, SD-2, and the risks in about four minutes. Committed on the plan branch as `d18a9cae`.

## Stage 3. PR plan

Splitter (opus): 2 minutes, 11 tool calls, checker clean. It proposed five PRs: the shared service, the old handlers delegating, the new controller split into reads and writes because one controller PR would be about 541 lines, and the interceptor path pattern last as a wiring PR.

Two things worth recording.

- The skill's line-estimation rule undercounted Java by about three times. The splitter noticed, counted against real handlers and the real 548-line test class instead, and wrote both counts in `Estimate basis`. The skill now says to calibrate against the repo first and treats the fixed numbers as a floor.
- The splitter raised a security observation outside its brief. `RequestHeaderInterceptor.postHandle` clears `customerId` and `clientId` from the Redis-backed session but leaves `customerSession`. A controller on a path the interceptor does not cover could serve a stale session with no `Authorization` header. With the interceptor pattern as the last PR, PR-3 and PR-4 would have been deployable unguarded. I folded the pattern into PR-3, dropped PR-5, re-ran the checker, and rewrote the rationale. Four PRs, estimates 310, 160, 280, 280.

Committed on the plan branch as `713d1348`. PR-1 branched from it. Second human gate took about three minutes.

Three practical findings, all now encoded in the plugin:

- The repo ignores `*.log`, so a plain `git add` would have silently dropped the raw test logs from the bundle. The verify command now force-adds the bundle and strips the rerun output directory, and the first commit I made had to be amended for exactly that reason.
- A plain `./gradlew check` on the head reported every task up to date and ran zero tests. The verifier caught it and re-ran with `--rerun-tasks`. The skill now has a "Fresh runs" section with the flag per build tool.
- The profile's summary command contains single quotes and does not fit the single-quoted slot in `rerun.sh`. The skill now says to write it to `artifacts/summary.sh` or use a one-line equivalent and say so.

A human who wants to check the result runs one command on a clean clone:

```bash

```

## What the exercise changed in the plugin

1. `/jstack:plan` and `/jstack:init` handle a repo that gitignores `docs/`.
2. The repo-profile skill confirms the checkout is on trunk before taking a baseline.
3. The pr-plan skill calibrates line estimates against real code instead of fixed numbers.
4. The verification-bundle skill forces fresh test runs, handles quoted summary commands, and requires per-PR scratch names for parallel verifiers.
5. `/jstack:verify` force-adds ignored logs and strips every rerun directory under the verification tree before committing.
6. Checker tests clean up their temp directories.
